1Overview and system map

The Notification Center lets internal admins publish in-app notifications to members of a book-subscription service, and lets each member read their own list in the app. There is no push, email, or SMS: "sending" a notification means creating a row that makes it appear in a member's in-app list.

1.1 Vocabulary

TermMeaning
NotificationThe admin-authored definition: image, headline, subheadline, link, type, and type-specific settings. One row in notifications. Addressed by an integer id on the admin surface only.
DeliveryOne notification landing in one member's list. One row in notification_deliveries. A member can hold several deliveries of the same notification (one per event occurrence, one per month for filter notifications). Addressed by an opaque public_id on the member surface.
Scheduled / liveA delivery with sent_at IS NULL is scheduled (invisible, waiting for due_at); once sent_at is set it is live.

1.2 System map

1.3 Three entry points

  • Admin surface — /admin/notifications…: list, get, create (filter / event / CSV import), import status, activate / deactivate / remove. Requires a session and the admin role.
  • Member surface — /notifications…: list my deliveries, get one, mark one clicked (a PATCH on the delivery). Requires a session; a member can only ever address their own deliveries.
  • Trigger interface — NotificationTrigger, an in-process TypeScript class called by business code. Not HTTP. Two calls: record(event) from the ship / enroll / pre-enroll code paths, and accountChanged(accountId) from every code path that changes an account's country, policy, relationship status, or credits.

2Behavior rules

These are the rules the implementation must satisfy. §2.1 is the complete operational rule set; §2.2 lists the product requirements they come from.

2.1 Rules

#RuleFrom
B1Visibility. A member sees a delivery if and only if all hold: it belongs to them; sent_at is non-null; sent_at is inside the window (B2); the parent notification is not removed. The notification's active flag plays no part in visibility.A9 R9
B2Window. In window ⇔ sent_at ≥ 00:00:00 UTC on the first day of the previous calendar month. A delivery sent Aug 15 is visible through Sep 30 and gone at Oct 1 00:00 UTC. Months are calendar months, not rolling periods.R4 A15 A28
B3Order. The member list is sorted by sent_at descending.R8
B4Active. active gates only the creation of new deliveries. Deliveries already live stay visible after deactivation. Creating a filter or event notification requires an explicit isActive; there is no default. CSV notifications are always active and the flag cannot be changed.R9 R18 A25 A26
B5Deactivate. Setting inactive cancels that notification's scheduled (unsent) deliveries: they never fire, even if the notification is reactivated later.A47
B6Remove. Remove-from-app hides the notification from every member immediately, including those who already saw it; cancels its scheduled deliveries; stops all future sends; is irreversible.R10 A18 A30 A36 A47
B7Filter eligibility. An account is eligible when it satisfies every filter: country ∈ selected set, policy ∈ selected set, relationship status ∈ selected set, credits ≥ minimum, credits ≤ maximum. Any filter that is omitted or empty imposes no constraint.R3 R15 A24 A45
B8Filter sends. While a filter notification is active, every eligible account receives it at most once per UTC calendar month. An account that becomes eligible later is sent it when the account changes (the business code reports the change, §7.2); a recurring rescan is the safety net for any change that was not reported. In a new month every still-eligible account receives a new delivery (new list entry, own timestamp, unclicked).R16 R17 A17 A21 A48 A56
B9Event sends. Each occurrence of the event produces one delivery per active event notification configured for that event. The same occurrence reported twice produces one. The spec's refer-a-friend example is handled as an enrolled event reported for the referrer: when a referred friend enrolls, the business code reports enrolled for the friend and again for the referrer (distinct occurrence keys), so two referrals mean two deliveries to the referrer.R14 A38
B10Event timing. shipped and enrolled: live at occurredAt + delay days (no delay → immediately). preenrollAudiobook: the event is the audiobook becoming available — business code reports it, once per member who pre-ordered, when the audiobook is published — and the delivery is immediate; any delay is ignored. This service never reads or schedules against a publication date.R12 R13 A19 A57
B11Trigger safety. Calling the trigger can never fail or roll back the business action that called it.A42
B12CSV sends. A CSV notification is delivered exactly once, at its liveDate, to every valid account id in the file. Repeated ids count once. Unknown ids are reported and skipped; the rest still send.R18 A10 A32 A43
B13Clicked. Each delivery has its own clicked flag, false until the app sets it with PATCH /notifications/:id, which it does only on the first open; the call is idempotent. Reading a delivery never changes it.R7 A35
B14Ownership. Member endpoints address deliveries by opaque public_id. Any id that is not a visible delivery of the caller (B1) yields the same 404, whatever the reason.A37 A40 A54
B15Time. Every stored and transmitted timestamp is UTC. The API emits ISO-8601 with a Z suffix; the "sent 5 minutes ago" label is computed by the client from liveDate.R6 A28
B16Retention. Notification records are kept forever and the admin list shows all of them. Deliveries that leave the window are moved to an archive table.A23 A51 A53
B17No double sends. All background processing is at-least-once; uniqueness on (notification, account, dedupe key) guarantees a retry never creates a second delivery.A46

3API contracts

3.1 Conventions

  • Resources, not commands. Every path names a resource; state changes are a PATCH on that resource carrying only the fields that change (activate, remove, mark clicked); re-processing an import creates a new run resource. There are no verb endpoints.
  • Naming. Booleans are isX; a resource's own identifier is id, and a reference to another resource is <resource>Id; type-specific fields are present only for their type.
  • Bodies are JSON (Content-Type: application/json) in both directions, except the multipart CSV upload. JSON keys are camelCase A27.
  • Notation. Bodies below are type specs, not examples: "name": type // description. Enum options are listed in the comment. Fields are required unless the comment says optional. Unknown request fields are rejected with 400.
  • Timestamps are ISO-8601 UTC strings, second precision, Z suffix — 2026-10-04T14:30:00Z. Request timestamps may be a full date-time with an offset or Z, or a plain date (2026-11-01); a plain date means midnight at the start of that day in the business timezone (BUSINESS_TIMEZONE, default America/New_York) and is stored as the equivalent UTC instant. Fractional seconds are rounded down to the whole second. Anything else → 400 A28.
  • Authentication. Every route requires a logged-in session → otherwise 401. Every /admin route additionally requires the admin role → otherwise 403 A2 A34 A44.
  • Pagination. List endpoints take limit (integer 1–25, default 25; larger values are clamped to 25; non-integers → 400) and cursor (opaque string from a previous response; malformed → 400). Responses are { "items": [...], "nextCursor": string | null }; null means no more pages A29.
  • Idempotent creates. The admin create endpoints (filter, event, import, import run) require an Idempotency-Key: <uuid> header (missing or not a UUID → 400). Re-sending a key with the same request returns that resource's current representation with the original status code and creates nothing; the same key with a different endpoint or body is a 400 A50.
  • Paths in, URLs out. Requests supply image and link as a path only; the service stores the path and builds the full URL in code when responding, by prefixing the site's base address, which is held outside this service's data A3. A valid path: starts with exactly one /; contains no scheme, host, //, backslash, ?, #, .. segment, whitespace, or control character. Anything else — including any full URL — is a 400. Because a host can never be supplied, a notification cannot point off-site.

3.3 Shared shapes

NotificationDetail — returned by the admin get, both creates, and the update:

{
  "id": integer,            // internal notification id
  "type": string,           // filter | event | csv
  "image": string,          // completed image URL
  "headline": string,       // headline text shown in the notification header
  "subheadline": string,    // secondary text shown under the headline
  "link": string,           // completed URL of the linked site page
  "isActive": boolean,      // whether new sends are enabled; for csv, true until removed
  "isRemoved": boolean,     // whether removed from app
  "createdAt": string,      // ISO-8601 UTC — when the notification was created
  "liveDate": string,       // present only when type = csv: the scheduled send date (ISO-8601 UTC)
  "activatedAt": string | null, // present only when type = filter or event: first activation time, null if never activated
  "filters": {              // present only when type = filter; absent keys mean "all"
    "country": string[],        // optional; "US" | "CA"
    "policy": string[],         // optional; "monthly" | "annual"
    "relationshipStatus": string[], // optional; "newMember" | "friend" | "bff"
    "credits": {                // optional
      "minimum": integer,       // optional; inclusive
      "maximum": integer        // optional; inclusive
    }
  },
  "eventTrigger": string,   // present only when type = event; shipped | enrolled | preenrollAudiobook (reported when the pre-ordered audiobook is published)
  "delay": integer | null   // present only when type = event; days after the event, null = none
}

Content field rules (all creates): image path ≤ 1024 and link path ≤ 2048 characters, both following the path rule in §3.1.

headline and subheadline are plain text and are sanitized on input:

  • Leading and trailing whitespace is trimmed; the result must be 1–255 characters.
  • Rejected with 400: the characters < and > (so no HTML or script tag can be stored); control characters, including line breaks and tabs; and Unicode direction-override characters (U+202A–U+202E, U+2066–U+2069), which can make text display differently from what was typed.
  • The value is stored and returned exactly as accepted, never HTML-encoded by the API. Clients must display it as text, not as HTML or markdown.

POST/admin/notifications/imports

Creates a CSV notification and starts its import A10 A43. Requires Idempotency-Key. Content-Type: multipart/form-data with exactly two parts:

Part file (CSV)

GET/admin/notifications/imports/:id

Status and row-level report of one import A43.

Response 200

{
  "id": integer,                // the import
  "notificationId": integer,    // the csv notification this import belongs to
  "status": string,             // processing | completed | failed
  "totalRows": integer,         // data rows in the uploaded CSV
  "accepted": integer,          // distinct valid accounts that received a delivery row
  "duplicatesIgnored": integer, // repeated account ids dropped
  "runs": [                     // every processing attempt, oldest first; `status` above is the latest run's
    {
      "id": integer,            // the run
      "status": string,         // processing | completed | failed
      "startedAt": string,      // ISO-8601 UTC
      "finishedAt": string | null,
      "error": string | null    // short reason when failed
    }
  ],
  "errors": [                   // one entry per distinct rejected id; empty while processing;
                                //   on `failed`, whatever had been collected before the failure
    {
      "row": integer,           // 1-based data-row number of the id's first occurrence
      "accountId": integer,     // the rejected account id
      "reason": string          // UNKNOWN_ACCOUNT
    }
  ]
}

Invariant when completed: totalRows = accepted + duplicatesIgnored + errors.length. errors lists every rejected id — it is not capped — so the totals always reconcile. accepted is the number of distinct ids in the file that exist as accounts; it is the same however many times the import job runs.

When status is failed (the job gave up after its last attempt): the counters and errors hold whatever was recorded before the failure, the file is kept so the import can be retried, and deliveries already created stay — they are correct deliveries, and re-running the import will not duplicate them. The admin fixes the cause and starts a new run of the same import (below); a new upload is not the way to recover, because it would create a second notification.

Errors: 401, 403, 404.

POST/admin/notifications/imports/:id/runs

Starts a new run of an existing import. An import is processed by runs: the upload creates run 1 automatically; if a run ends failed, an admin creates another. A run re-processes the same file for the same notification; the job is idempotent, so accounts already delivered to are skipped and the report is rebuilt from scratch. Requires Idempotency-Key like the other creates. No request body.

Response 202

{

  "importId": integer,       // the import it belongs to
  "notificationId": integer
}

Errors: 401, 403, 404; 409 CONFLICT if the import's latest run is not failed (a run is already in progress, or the import completed).

5Storage schema

MySQL 8 dialect (Aurora MySQL 3). Worker and API sessions run at READ COMMITTED, so range scans such as due-send do not gap-lock the rows other jobs are inserting. All DATETIME columns hold UTC; the application never writes local time A28. Table and column names are snake_case A27. Tables use utf8mb4; the random-id columns are ASCII with a binary collation so comparisons are case-sensitive. created_at columns are set by the database default (they are informational); every timestamp the design reasons about — sent_at, due_at, cancelled_before, live_date — is written by the application from its clock, truncated to whole seconds.

dedupe_key is how rule B17 is enforced. The application sets it on every insert, and a repeat insert with the same (notification, account, dedupe key) is skipped:

Typededupe_keyEffect
eventthe occurrence key (same value as occurrence_key)the same occurrence reported twice inserts once A38
filterUTC month of the send, 'YYYY-MM'one delivery per account per calendar month A17 A21
csvthe literal 'import'one delivery per account per notification

How deliveries are inserted. Every delivery insert in the codebase goes through one helper, lib/insertDeliveries.ts. It skips only a genuine repeat and surfaces everything else:

INSERT INTO notification_deliveries (public_id, notification_id, account_id, sent_at, due_at, ...)
VALUES (...), (...)
ON DUPLICATE KEY UPDATE id = id;      -- a duplicate becomes a no-op; nothing else is suppressed
  • INSERT IGNORE is not used anywhere. It would also hide a missing account, a missing required value (stored as a zero date, which then sends immediately), a truncated key, and a public_id clash. The connection runs in strict SQL mode so those raise errors.
  • Repeat (same notification, account, dedupe key): no-op, counted as "already delivered". This is the only silent case.
  • public_id clash: the statement cannot tell this from a repeat, so when fewer rows were inserted than sent, the helper re-reads which (notification, account, dedupe key) triples of the batch now exist. Any that are still missing clashed on public_id; they get fresh ids and are inserted again.
  • Account does not exist (foreign-key error): the statement fails and the helper returns the offending account ids to the caller. The event job logs the unknown account and drops the event; the fan-out drops that account from the page; the import records it as UNKNOWN_ACCOUNT.
  • Any other error propagates, and the job retries.

The helper returns { inserted, alreadyDelivered, unknownAccounts }, which is what handlers count and log from.

A dedicated NOT NULL column is used because MySQL unique indexes admit unlimited NULLs, so a nullable occurrence_key alone could not constrain filter and csv rows. Account deletion cascades to live deliveries A52.

5.4 Filters

A filter notification's filters live in the notifications.filters JSON column, in exactly the shape the API accepts and returns (§3.3) — no separate tables, no join, and no translation between stored and wire forms:

-- notifications.filters for "Canadian friends and BFFs with at least one credit":
{"country": ["CA"], "relationshipStatus": ["friend", "bff"], "credits": {"minimum": 1}}

-- "everyone":
{}
  • A key that is absent imposes no constraint — that is how "omitted = all" is stored A24 A45. Empty arrays are removed on write so they never appear.
  • Values are stored as the API spells them; the accounts adapter (§6.4) translates to the accounts table's own values at query time.
  • The column is NULL for event and csv notifications.
  • Validity is guaranteed by the request schema (§9.2). Optionally, a CHECK (JSON_SCHEMA_VALID(...)) constraint on the column mirrors that schema as a database-level backstop.
  • Filters are only ever read one notification at a time, to build the eligibility query; nothing searches notifications by filter value. If that is ever needed, MySQL's JSON functions and multi-valued indexes cover it.

  • knex migrations, forward-only. No down-migrations in production; rollback is the previous image on a compatible schema (§11.3).

7Core flows

7.1 Event notification

  1. Business code calls trigger.record(event) after its own write has committed.
  2. The trigger enqueues one event_delivery job carrying the event. No reads, no lookups.
  3. It returns. Errors are swallowed and counted (B11).
  4. The queue delivers the job to a worker.
  5. The handler loads active, non-removed event notifications whose event_trigger matches. For each it computes due_at (B10) and inserts one delivery with dedupe_key = occurrenceKey. If due_at ≤ now the row is inserted already live (sent_at = now). A repeat of the same occurrence hits the unique index and inserts nothing (B9).
  6. For rows inserted scheduled (a shipped or enrolled notification with a delay), the due-send job sets sent_at once due_at passes.
  7. The member API returns the delivery because it now satisfies B1.

7.2 Filter notification

  1. An admin activates a filter notification (or creates it with isActive: true).
  2. After the write that sets active commits, the API enqueues fanout_filter { notificationId }. If that enqueue fails the request still succeeds and the failure is logged: the next rescan enqueues the same job, so the send is delayed, not lost.
  3. The API responds; the send proceeds in the background.
  4. The queue delivers the job to a worker.
  5. It takes the next range of 10,000 account ids and selects the eligible accounts in it (§6.4) that have no delivery of this notification with this month's dedupe key.
  6. It inserts that batch through the idempotent insert helper (§5.3), live immediately — send time and 'YYYY-MM' key taken from the same instant.
  7. Before the next batch it re-checks that the notification is still active and not removed and that the month has not changed, and renews its job lease. It stops when any check fails or the ranges are exhausted.
  8. The rescan schedule enqueues the same job for every active filter notification: daily as the safety net for unreported account changes, and just after each month starts to produce that month's send (B8).

When an account changes

Fan-out and rescan cover "everyone who matches now". Rule B8 also requires that an account which comes to match is sent the notification then, not at the next scan. Two mechanisms do this together A56:

  1. Reported changes (immediate). Business code calls trigger.accountChanged(accountId) after committing any change to the four filter attributes. That enqueues account_recheck { accountId }. The handler evaluates that one account against every active filter notification (the §6.4 query with AND a.id = :accountId) and inserts a delivery for each one it matches and has not received this month.
  2. Event-driven changes (free). The event_delivery handler runs the same per-account check after it finishes, because shipping and enrolling usually change credits or status. No extra call from business code is needed for those three paths.
  3. Rescan (safety net). Anything not reported — a missed call site, a batch job, a manual database fix — is caught by the daily rescan.

Call sites business code must cover (these live outside this repository; this service provides the method and the tests, not the calls): account creation / enrollment; credit grant, spend, refund, expiry, and manual adjustment; plan (policy) change; relationship-status change; country change; any admin or support tool and any batch job that writes those columns.

7.3 CSV import

  1. The admin uploads the notification fields and the CSV.
  2. The API stream-parses the file: header, integer rows, size and row caps. Any violation → 400, nothing stored.
  3. One transaction inserts the csv notification (active = TRUE), the imports row (total_rows set), run 1 in import_runs, and the import_files row; after it commits the API enqueues process_import { importId, runId }. If that enqueue fails the request still returns 202; housekeeping re-enqueues imports left in processing (§8.3).
  4. The API responds 202 with the import's id.
  5. The queue delivers the job to a worker, which reads the file.
  6. It de-duplicates ids in memory, then checks existence against accounts in chunks of 1,000.
  7. Existing ids get a delivery (due_at = live_date, dedupe_key = 'import'; already live if live_date ≤ now).
  8. Unknown ids are collected as the chunks go by (and the job heartbeats between chunks).
  9. At the end, one transaction writes every error row and the counters, sets completed, and deletes the file row.
  10. The admin polls the import resource for status and the report.
  11. At liveDate, due-send makes the deliveries live.
  12. Only if a run ended failed: the admin creates a new run, and steps 5–9 repeat on the same file.

7.4 Deactivate and remove

The request only changes the notification row, so it returns immediately however many deliveries are waiting. In updateNotification.ts:

BEGIN;
SELECT * FROM notifications WHERE id = :id FOR UPDATE NOWAIT;   -- lock busy → 409; no row → 404; removed → 409
-- deactivate:
UPDATE notifications SET active = FALSE, cancelled_before = :now WHERE id = :id;
-- remove:
UPDATE notifications SET removed = TRUE, active = FALSE, cancelled_before = :now WHERE id = :id;
COMMIT;
-- after commit: queue.enqueue('cancel_scheduled', { notificationId })

Cancellation is enforced where deliveries are released, not by the request. The due-send job (§8.3) refuses to release a scheduled delivery, and deletes it instead, when any of these holds for its notification:

  • it is removed;
  • it is inactive;
  • the delivery was created at or before cancelled_before — this is what keeps a delivery cancelled even if the notification has since been reactivated (B5).

This closes the race where a job that had already read the notification as active inserts a scheduled delivery just after the deactivation commits: the row exists, but it can never be released.

The cancel_scheduled job is only tidying: it deletes the same rows in chunks of 5,000 so they do not sit in the table until their due_at. If that enqueue is lost, housekeeping runs the same cleanup within five minutes. Jobs already in flight also stop on their own: fanout_filter re-checks between pages, event_delivery only considers active notifications, and process_import re-checks removed between chunks.

7.5 Member reads

One query shape, in member/visibility.ts, backs all three member operations. It is rule B1:

SELECT d.id, d.public_id, d.notification_id, d.is_clicked, d.sent_at
FROM notification_deliveries d
JOIN notifications n ON n.id = d.notification_id
WHERE d.account_id = :caller                      -- ownership (B14)
  AND d.sent_at IS NOT NULL                       -- live, not scheduled
  AND d.sent_at >= :windowStart                   -- first instant of the previous UTC month (B2)
  AND n.removed = FALSE                           -- not removed (B6)

-- list variant appends:
  AND (d.sent_at, d.public_id) < (:cursorSentAt, :cursorPublicId)   -- only when a cursor is given
ORDER BY d.sent_at DESC, d.public_id DESC         -- B3; public_id is the stable tie-break
LIMIT :limit + 1                                  -- the extra row signals another page

-- detail and clicked variants append instead:
  AND d.public_id = :id                           -- zero rows → 404
  • Cursor. base64url(JSON.stringify({ s: sentAtIso, p: publicId })) of the last returned item. It is built from public_id, never the internal id, so decoding a cursor reveals nothing a member does not already have.
  • Content. Headline, subheadline, image key, and link path are selected in the same query from the joined notifications row, then URLs are composed. There is no cache: the join is already there to check removed, so returning four more columns costs nothing.
  • Clicked (PATCH). Run the query with public_id = :id; zero rows → 404; else UPDATE notification_deliveries SET is_clicked = TRUE WHERE id = :internalId AND is_clicked = FALSE and return the delivery with isClicked: true regardless of rows changed.

8Background work and failure handling

8.1 Queue: the contract, and the temporary implementation

What the rest of the system relies on. Producers and handlers see only the Queue interface (§6.3) and assume exactly this, which any real queue provides:

  • At-least-once delivery. A job may arrive twice or concurrently with itself. This is safe because every delivery insert skips a repeat of uq_delivery_dedupe (B17, §5.3) and every handler recomputes its outputs from scratch.
  • No ordering and no transactional enqueue. An enqueue is a separate step after the database commit. Each producer therefore has a recovery path if that step is lost: rescan for fan-outs, housekeeping for imports (§8.3). A lost event job is the one unrecovered case (§13.3).
  • Retry, then dead-letter. A throwing handler is retried with backoff; after the last attempt onDead runs once (it marks an import failed and raises the dead-job alarm).
  • Leases. Long handlers (fan-out, import) call ctx.heartbeat() after every page.
  • Delayed delivery via runAt, used only for retry backoff.

What ships now: dbQueue.ts, a stand-in. It implements the interface on the jobs table so the whole system can be run and demonstrated without the company queue. It is deliberately simple and will not scale — polling and row locks on one table — and is expected to be replaced, not tuned:

-- claim: each worker polls every second while idle, up to 10 jobs
BEGIN;
SELECT id FROM jobs
 WHERE status = 'queued' AND run_at <= UTC_TIMESTAMP()
 ORDER BY run_at, id LIMIT 10
 FOR UPDATE SKIP LOCKED;
UPDATE jobs SET status = 'running', locked_by = :workerId, locked_at = UTC_TIMESTAMP(),
                attempts = attempts + 1
 WHERE id IN (:ids);
COMMIT;
  • Success → done. Handler throws → queued with run_at = now + 2^attempts minutes and last_error; fifth failure → dead, then onDead.
  • heartbeat() refreshes locked_at. The stand-in's own consume() loop also does its upkeep once a minute: re-queues running jobs with locked_at older than JOB_LEASE_MINUTES, and deletes done rows older than 7 days.
  • It deletes its own done rows older than 7 days; dead rows are kept for inspection and purged by housekeeping after 30 days.

Replacing it means adding one adapter file that implements Queue against the real system, selecting it in worker.ts / api.ts, and dropping the jobs migration. The queue contract tests (§10.2) run against whichever implementation is configured.

8.3 Scheduled jobs

Why scheduled sends are rows rather than delayed queue jobs: a row can be cancelled when the notification is deactivated or removed (§7.4); a message already sitting in a queue with a delay cannot be. The queue is therefore never asked to hold a delay longer than a retry backoff.

Due-send runs on every worker: its FOR UPDATE SKIP LOCKED selection already lets several workers release different batches at once, which is what keeps a million deliveries falling due together from taking minutes on one process. The other three jobs run on one worker at a time: it holds GET_LOCK('notification_center_scheduler', 0) on a dedicated connection and runs their timers; if that worker dies the lock releases and another takes over on its next attempt (every 30 s). Each run records start, completion, and status in scheduled_runs.

9.4 Idempotent creates

A key is remembered together with the endpoint it was used on and a SHA-256 of the request body (for the import, the JSON part plus the file). 9.7 No response caching; how remove propagates

The service caches nothing. Every member request evaluates ownership, sent state, window, and removed in SQL (§7.5) and reads the notification text in the same query. A remove therefore takes effect for every member on their very next request, on every instance, with nothing to invalidate. This is how "removed propagates immediately" A36 is met. The architecture's suggestion of response caching with purge-on-remove was judged not worth its complexity for this read path (see §14.4).

9.8 Rate limiting and upload caps

A fixed one-minute window counter per (surface, accountId), held in memory per instance: 120 requests/min on member routes, 600 on admin routes; excess → 429 RATE_LIMITED with a Retry-After header. The numbers are starting points A33.

Close second: a Redis sliding window — exact across instances, one more datastore. Per-instance counting is acceptable for a coarse abuse guard.

10.1 Unit tests

Pure functions and single classes, no database and no HTTP. Fast; run on every save.

  • NotificationTrigger: with a FakeQueue, record() and accountChanged() each enqueue exactly one job with the right payload; with a queue whose enqueue rejects, both resolve without throwing and count the failure.
  • Zod request schemas: each endpoint's schema accepts its valid shapes and rejects each invalid one (missing field, unknown key, bad enum, invalid path, past liveDate).
  • Time math: windowStart and monthKey at month and year boundaries — sent 2026-08-31T23:59:59Z is out of window at 2026-10-01T00:00:00Z; sent 2026-09-01T00:00:00Z is still in.

  • Path handling: valid path kept and composed into a full URL on output; rejected: any full URL, //evil.com/x, /\\evil.com, a query string or fragment, .. segments, whitespace and control characters, a missing leading slash.
  • Cursor codec round trip and rejection of garbage; public id format.
  • Headline / subheadline sanitizer: trims; accepts ordinary punctuation and non-Latin text; rejects <script>, a lone <, a line break, a direction-override character, an empty or whitespace-only value, and 256 characters.
  • CSV shape validator: BOM, CRLF, trailing blank lines, bad header, non-integers, caps.

10.2 Integration tests

Real MySQL (with the seeded stand-in accounts) and the real stand-in queue, but no HTTP: job handlers and scheduled jobs are called directly, and results are asserted in the database. These prove the background machinery.

  • Insert helper: a repeat is a no-op; a forced public_id clash is re-inserted with a new id and the delivery exists; an unknown account is returned, not swallowed; a missing required value raises.
  • Idempotency: run fanout_filter twice → same row count; record() twice with one occurrence key → one delivery, with two keys → two; process_import twice → same deliveries and report; due-send twice → sent_at unchanged.
  • Account change: an account that becomes eligible and calls accountChanged gets the delivery as soon as the job runs, with no rescan; calling it again adds nothing; an account that no longer matches gets nothing; an event for an account also triggers the check; accountChanged with a failing queue resolves without throwing.
  • Filter: account becomes eligible after the first fan-out and is not reported → next rescan adds exactly that account; clock moved into the next month → everyone eligible gets a second delivery; deactivated mid-run → stops.
  • Event: immediate; delayed (scheduled, then live after the clock advances and due-send runs); pre-enroll immediate even when the notification has a delay; inactive notification → nothing; two notifications on one event → two deliveries.
  • Trigger safety: record() with a queue whose enqueue rejects resolves without throwing and increments the failure metric.
  • CSV: duplicates and unknown ids → report matches; future liveDate → invisible until due-send after the clock passes it; removed before send → never appears.
  • Cancellation: a scheduled delivery inserted just after a deactivation commits is deleted by due-send, not sent; deactivate then reactivate → deliveries scheduled before the deactivation still never send, ones created after reactivation do; cancel_scheduled removes the rows; with that job lost, housekeeping removes them.
  • Expiry: out-of-window rows move to the archive byte-for-byte and leave the hot table; in-window rows stay.
  • Queue contract (run against the configured implementation): an enqueued job reaches its handler; a throwing handler is retried; the final failure calls onDead once. Stand-in specifics: stale running jobs are re-queued; two concurrent claimers never take the same job.
  • Trigger end to end inside the worker: record() → stand-in queue → event_delivery handler run once → delivery row exists with the expected due_at, dedupe_key and sent_at.
  • Lost enqueue: with a queue that drops the enqueue, an activated filter notification is still sent by the next rescan, and a stuck import is picked up by housekeeping.
  • Most of these use FakeQueue.runAll() to run handlers on demand; the queue-contract tests and the "trigger end to end inside the worker" test use the real stand-in queue.

11Deployment, rollback, observability

11.1 Topology

One container image, two services: api (node dist/api.js, at least two tasks behind the load balancer) and worker (node dist/worker.js, at least one task, no ingress). Extra workers add queue throughput; only the lock holder runs the scheduler. Target runtime is ECS Fargate — a placeholder for whatever the company already runs; nothing in this design depends on it.

Close second: one combined process — simpler, but a large fan-out would compete with API latency.

11.2 Deploy

CI builds the image. Migrations run as a release step before new tasks take traffic. Because schema changes follow expand → contract (§5.8), old and new code both work against the schema during a rolling deploy.

11.3 Rollback

Redeploy the previous image. There are no down-migrations; the newer schema is compatible with the older code by construction. A failed migration aborts the release before any task is replaced.

11.4 Observability

13Risks accepted

13.1 The queue in this build is a stand-in

The jobs-table queue is temporary: enough to run and demonstrate every flow, not built to scale (one polled table, row-lock contention under load). Accepted because the production queue already exists and this service should not grow its own. The cost is contained by the Queue interface — nothing outside src/queue knows which implementation is running. Until the real adapter exists, the stand-in is the throughput ceiling.

13.2 Whole-base fan-out writes

A filter matching every member writes one row per member, in 1,000-row pages. The cost is elevated write load during a campaign, visible in the fan-out metrics. Accepted because cheap reads, per-delivery clicked state, and the once-per-month rule all depend on the rows existing A4.

13.3 An event can be lost between commit and enqueue

The trigger enqueues after the business write commits and swallows failures (B11), so a crash or queue outage in that gap loses the notification for that occurrence; it is counted and alarmed, not recovered. Accepted to keep the business path free of this service's failures. The improvement before production use, if losses matter, is an outbox: the trigger writes a row in the business transaction instead of enqueueing, and a relay in the worker moves unsent rows to the queue — never lost, only delayed. Not designed in yet because it depends on the business code's transaction boundaries. Separately, the trigger does no lookups, so every occurrence costs one job even when no notification is configured for it.

13.4 Immediate sends can lag by a poll interval

An "immediate" event delivery appears after the worker's next poll (about a second); a scheduled one up to 60 seconds after due_at. The member-facing timestamp starts from the actual go-live, so it is never wrong, only slightly later than the event.

13.5 Cascade delete cost

Deleting an account with a long delivery history is a heavier statement because of the cascade A52. Account deletion is rare; chunked pre-deletion is the fallback if it ever hurts.

13.6 Per-instance rate limits

Limits are enforced per API instance, so the effective ceiling scales with instance count.

13.7 Chosen numbers are starting points

Rate limits, CSV caps, batch sizes, poll and due-send intervals, and the daily rescan are configuration, expected to be tuned A33. The page size of 25 is not — it is contract.

13.8 Immediate eligibility depends on call sites this service does not own

"Sent when the account changes" is only as complete as the list of places business code calls accountChanged. A missed or future call site degrades silently to the rescan's latency (up to a day) — never to a lost send. Accepted because the calls cannot be built or verified from this repository; the rescan exists precisely so a gap is slow rather than wrong. A changed-then-reverted account can still be missed if the revert lands before the job runs (seconds).

13.9 An import report can be very large

The import report returns every rejected id with no cap, so a file of mostly unknown ids produces a response of up to a million entries (tens of megabytes). Accepted because real files are overwhelmingly valid and an uncapped list keeps the report exact. If it becomes a problem, the fix is to page the error list.
