Notification Center: architecture and code audit

An audit of the agent-written code in src/, migrations/ and scripts/, built to help you decide what to read by hand and in what order. Audited at commit 20eff41 on 2026-10-06.

The delivery logic is careful and consistent. The system around it is not yet deployable. Every delivery row goes through one insert function, one cancellation rule and idempotent job handlers, and the concurrency reasoning is written down next to the SQL it protects.

The gaps are at the edges: auth and the queue exist only as stand-ins that refuse to start in production, the event flow has no caller inside this repo, and the service reaches straight into the host application's accounts table. Several background paths also cost more than they need to as data grows.

Start with the test audit: where the tests assert less than, or something other than, the design says.

If you only have four hours, read tier 1: what each job and handler does to rows, which is where every invariant lives.

Delivery lifecycle

A delivery is one notification for one account. Its state is not a column; it is whether sent_at is set and which table the row is in.

The cancellation rule

An unsent delivery is cancelled when its notification is removed, or inactive, or was deactivated at or after the delivery was created (d.created_at <= n.cancelled_before). The third clause is what keeps old scheduled rows dead after a notification is switched back on. It works only because both timestamps are written from the application clock, which is why every caller passes a fresh clock.now() into insertDeliveries.

The three notification types differ in what starts them and in the key that prevents a second delivery.

Every admin write follows the same shape: commit the row, then enqueue, and if the enqueue fails log it and return success anyway (src/admin/enqueueAfterCommit.ts). That is only safe because a timer later notices the missing work. When you read a handler, find its safety net: rescan and housekeeping for fan-outs, housekeeping for stalled imports, due_send for cancellations. Event jobs have none; a failed trigger enqueue is logged and lost.

Queue and timers

Jobs are rows in a table. A worker owns a job only while its lease is fresh.

The leader is whichever worker holds a MySQL named lock on a dedicated connection. Ownership is re-verified against the database before each leader-only run, and the code states that a brief two-leader window is still possible, so leader-only timers are written to be idempotent.

Findings

High: decide before integrating

H1Owner: no action (build-issues 1)Neither process can start in production, and the image defaults to production

src/config/index.ts:99-103 · src/api.ts:19-27 · src/queue/index.ts:8-17 · Dockerfile:15

Status: Owner decision 2026-10-07 on build-issues 1: no action. The real auth provider and queue adapter remain unbuilt features; the production refusal stays as the guard.

The only auth provider trusts an X-Account-Id header, and the only queue is the jobs table. Both are refused when NODE_ENV=production, and no alternative exists. The Dockerfile sets NODE_ENV=production, so the built image exits on start for the API and the worker alike. CI only checks that it refuses to start without config.

The guard is an exact string match. Run with any other value (staging, or unset) and the service accepts any caller's claimed account id, with accounts 1, 2 and 3 as admins by default.

Do: treat the real AuthProvider and the real Queue adapter as unbuilt features, not configuration. Consider inverting the guard so stand-ins need an explicit opt-in rather than the absence of one word.

H2Owner: deferredThe event flow has no caller and no defined way to be called

src/trigger/index.ts:57-152 · src/admin/createEvent.ts:1 · package.json

Status: Deferred by the owner 2026-10-07: the event flow's caller is the business code importing NotificationTrigger; how it is called is decided when integrating.

NotificationTrigger is the only way an event or an account change reaches the system, and nothing in this repo calls it. There is no HTTP endpoint for it, although a comment in createEvent.ts refers to "the trigger endpoint". package.json has no main or exports, so how the host imports the class is undefined.

When the host does call createNotificationTrigger(config), it opens its own MySQL pool into this service's database and keeps it for the life of the process. In production that call throws, for the reason in H1.

Do: pick the integration shape (published package, or an internal HTTP endpoint) and write the first real caller. Until then two of the five job types are exercised only by tests.

H3Owner: deferredThe service is bound to the host's accounts table at the database level

migrations/20261001000100_initial.ts:50 · src/eligibility/accountsSchema.ts · src/jobs/processImport.ts:87 · src/lib/insertDeliveries.ts:58

Status: Deferred by the owner 2026-10-07: the accounts coupling (foreign key, cascade, lock interactions) is accepted for now; see build-issues 61 and 65.

Deliveries carry a foreign key to accounts(id) with ON DELETE CASCADE; eligibility is a direct SQL query over four accounts columns. This forces the service into the same MySQL schema as the host and makes the host's account writes participate in this service's locking: account deletes cascade through delivery rows and can deadlock with expiry, and each due_send batch holds shared locks on up to 1,000 account rows.

Column names are isolated in one adapter file, which helps with renames but not with the coupling itself. There is also no index requirement stated for the filter columns; a fan-out is a range scan over account ids with the filter applied per row.

Do: confirm with whoever owns accounts that a foreign key from another service and these lock interactions are acceptable. If not, this is a schema change, and insertDeliveries relies on the foreign key to detect unknown accounts.

Medium: cost and operations

M1Owner: deferredFan-out work scales with notifications × accounts, every day

src/scheduler/rescan.ts:18-31 · src/jobs/fanoutFilter.ts:62-104 · src/scheduler/housekeeping.ts:38-52

Status: Deferred by the owner 2026-10-07: the daily rescan cost is accepted for now; the mitigations (spread the schedule, scan accounts once for all filters, change-tracked rescans) are noted for later.

The daily rescan enqueues a fan-out for every active filter notification, and each fan-out walks the entire accounts table in 10,000-id ranges with a NOT EXISTS against deliveries. After the first run of the month almost every pass finds nothing to do, but still scans everything.

Housekeeping adds to this: every five minutes it enqueues a fan-out for any active filter notification with no delivery this month. A notification whose audience is empty therefore gets 288 full-table fan-outs a day, indefinitely (the comment calls this "by design"). Nothing prevents several identical fan-outs being queued at once.

Do: estimate with real numbers (active filter notifications × account count). Recording "fan-out completed for month M" on the notification would remove most of the repeat work.

M2Resolved in c35e87eEvery event re-evaluates the account against every active filter notification

src/jobs/eventDelivery.ts:140 · src/jobs/accountRecheck.ts:28-34, 64

Resolved: recheckAccount now reads the account's deliveries for the month once, up front, and skips every notification already delivered, so those no longer cost an eligibility query or a duplicate insert. The finding as first written follows.

Each event_delivery job ends with recheckAccount: for each active filter notification, one eligibility query and, on a match, one insert attempt, all on the writer. There is no check for "already delivered this month" before the insert, so most attempts are duplicates that the unique key absorbs. Each such duplicate also consumes an auto-increment id.

Do: multiply expected events per day by active filter notifications. If that is large, check existing deliveries for the account in one query first.

M3Resolved in ab7cf3aThe scheduler never catches up on a missed run

src/scheduler/index.ts:5-7, 61-68 · src/scheduler/schedule.ts:7-9, 60

Resolved: on becoming leader the scheduler reads scheduled_runs once; a leader-only cron timer whose most recent due time (Schedule.previousDue) is later than its last start runs once at the next tick. One catch-up run per timer, never one per missed occurrence; a timer with no recorded start (NULL) is not caught up. The finding as first written follows.

A cron timer fires only if a tick happens during its matching minute. Last-start times are held in memory; the scheduled_runs table is written on every run and never read. If no worker is leader during 01:00 UTC (a deploy, a crash, a 30-second leader handover), that day's expiry does not run. The same applies to the 06:00 rescan and the month-start rescan at 00:05 on the 1st, which is the run that sends each month's filter notifications promptly.

Do: on start, read scheduled_runs and run anything whose last start predates its most recent due time. The table already holds what is needed.

M4Owner: deferredDeploys cost long jobs an attempt and a 15-minute stall

src/worker.ts:48, 83-87 · src/queue/dbQueue.ts:254, 379-405

Status: Deferred by the owner 2026-10-07: worker shutdown and lease behaviour belong to the queue stand-in, which the company queue replaces.

On shutdown the worker waits 30 seconds for running handlers, then exits. A job still running stays marked running until its 15-minute lease expires and upkeep re-queues it. Attempts are counted at claim time, so each interruption spends one of five. Fan-outs are the longest jobs and the most exposed: five unlucky deploys dead-letter one, after which only the next daily rescan recovers it.

Do: on shutdown, release unfinished jobs back to queued without spending the attempt, or give handlers a stop signal to check between chunks.

M5Owner: deferredQueue upkeep scans every finished job, on every worker, every minute

src/queue/dbQueue.ts:426-433 · migrations/20261001000200_jobs.ts:16

Status: Deferred by the owner 2026-10-07: queue upkeep cost belongs to the queue stand-in, which the company queue replaces.

Old done rows are deleted by status = 'done' AND locked_at < cutoff, but the only index is (status, run_at). Each pass reads every done row from the last seven days to find none to delete. With one job per shipment or enrolment this grows steadily, and every worker repeats it each minute.

Do: if the table queue survives beyond development, add (status, locked_at) or run this delete from housekeeping on the leader only.

M6Owner: deferredCSV uploads are parsed in the API process and stored in MySQL

src/admin/createImport.ts:30-34, 89-92, 122 · src/admin/csvShape.ts:15-33 · migrations/20261001000100_initial.ts:80

Status: Deferred by the owner 2026-10-07: CSV parsing in the API process and file storage in MySQL are accepted at the stated caps; revisit if upload sizes grow.

An upload of up to 10 MiB is buffered in memory, decoded, parsed to an array of up to a million ids on the request path, then written as one MEDIUMBLOB row. Several concurrent uploads multiply that; nothing limits concurrency. MEDIUMBLOB holds 16 MiB, so setting CSV_MAX_BYTES above that turns valid uploads into a 500 at insert time.

Do: cap CSV_MAX_BYTES at the column size in config validation. Longer term the file belongs in object storage.

M7Owner: deferredRate limits are per process and skip unauthenticated traffic

src/middleware/rateLimit.ts:17-26 · src/app.ts:61-62

Status: Deferred by the owner 2026-10-07: per-instance limits were accepted in the design (§13.6); the unauthenticated-traffic half is on the test-audit list (group D).

Counters live in each API instance's memory, so the effective limit is the configured one times the number of instances, and it resets on restart. The limiter runs after auth, so requests that fail with 401 are never counted.

Do: fine as a stand-in. Decide whether the real limit lives at a gateway before relying on these numbers.

Low: edges and consistency

L1Owner: not important for now (build-issues 76)Same-second deactivate and reactivate can cancel a fresh delivery

src/lib/cancellation.ts:14 · src/admin/updateNotification.ts:47

Status: Owner decision 2026-10-07 on build-issues 76: not important for now; left as built.

Both timestamps are whole seconds and the rule uses <=. It needs an admin double-toggle and an event in the same second, so it is rare, but it is a silent loss.

L2Owner: deferred (scheduler plumbing)A slow leader check lets overlapping ticks pick the same timer

src/scheduler/index.ts:115-127

Status: Deferred by the owner 2026-10-07. Scheduler mechanics are plumbing, not domain behaviour; leader-only timers are idempotent, so an overlapping pick costs a duplicate run, never a duplicate send. Revisit with the other before-production items.

A tick builds its due list, awaits the leader verification (up to 5 seconds), and only then records the start. Ticks fire every second, so later ticks see the same timer as due. Usually the second one records a spurious skipped; if the first run finishes fast enough the timer runs twice. What holds up

Things you can lean on while reading, so you can spend attention elsewhere.

  • single paths One insert function for deliveries, one SQL definition of "cancelled", one visibility query for members, one CSV reader shared by upload validation and the job. Changes to a rule have one place to go.
  • idempotent handlers Every job handler tolerates duplicates and concurrent copies of itself, which is what makes the "enqueue failed, carry on" pattern and at-least-once delivery safe.
  • injected clock All time comes from deps.clock and is bound as a parameter; no SQL NOW(). This is why the time-dependent rules are testable and why the cancellation comparison is sound.
  • no hidden globals Two composition roots (api.ts, worker.ts) build a Deps object passed everywhere. The one module-level cache is in trigger/index.ts:127.
  • strict input zod strict objects reject unknown keys on every body and query; text fields refuse control and direction-override characters; cursors are validated and bound to the filters they were issued under.
  • log hygiene The database layer strips interpolated SQL from errors (src/db/index.ts:44) so notification content does not reach logs.
  • clean build Typecheck and lint pass with no suppressions; there are no TODO or FIXME markers and nine uses of any in total.
A caution on the tests. 2.4 lines of test per line of source is a lot, and they were written by the same agent as the code, so they confirm the code does what its author intended. They cannot tell you whether the intent matches the spec. When you read a tier 1 file, open its integration test and check what the assertions actually pin down.
